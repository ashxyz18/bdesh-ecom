# Template Upload System - Manifest-Driven Architecture Plan

## Goal
Build a **template-agnostic platform** where ANY React/static template can be uploaded, auto-built, and configured through a dynamic dashboard — without code changes per template.

## Core Problem
The user wants a **versatile dashboard** that adapts to every template type:
- **Nike** (test) needs: hero headline, banner text, brand colors, product categories
- **SAS** (future) might need: collections, lookbooks, size guides
- **Restaurant** (future) might need: menu items, opening hours, table reservations
- **Portfolio** (future) might need: projects, skills, about section

The dashboard must render **different config forms for every template** without code changes.

---

## Architecture Overview

### The Template Contract

Every template provides a **`manifest.json`** that declares:
1. **What data it needs** from the platform (`api.mappings`)
2. **What config sections it exposes** to merchants (`configSchema`)
3. **How to render** (`entryPoint`, `type`)

```
Template Manifest (declares needs)
         ↓
Dashboard reads configSchema → renders dynamic forms
         ↓
Merchant configures → saved to Store.settings JSON
         ↓
Store page serves template via /api/templates/serve
         ↓
Serve route injects window.__PLATFORM_CONFIG__
         ↓
Template reads injected config → applies to UI
```

### Manifest Format

```json
{
  "id": "nike",
  "name": "Nike Store",
  "version": "1.0.0",
  "entryPoint": "index.html",
  "type": "react",
  "previewUrl": "/templates/nike/index.html",
  
  "api": {
    "mappings": {
      "products": {
        "id": "id",
        "name": "name",
        "price": "price",
        "image": "images[0]",
        "category": "tags[0]",
        "salePrice": "comparePrice"
      }
    }
  },
  
  "configSchema": {
    "hero": {
      "label": "Hero Section",
      "fields": {
        "headline": { "type": "text", "label": "Headline", "default": "Get More Out of Every Run" },
        "subtext": { "type": "text", "label": "Subtext", "default": "Discover the latest gear" },
        "image": { "type": "image", "label": "Hero Image" },
        "ctaText": { "type": "text", "label": "CTA Button", "default": "Shop Now" }
      }
    },
    "banner": {
      "label": "Promo Banner",
      "fields": {
        "text": { "type": "text", "label": "Banner Text" },
        "color": { "type": "color", "label": "Background Color", "default": "#111111" }
      }
    },
    "theme": {
      "label": "Brand Colors",
      "fields": {
        "primaryColor": { "type": "color", "label": "Primary", "default": "#000000" },
        "accentColor": { "type": "color", "label": "Accent", "default": "#e74c3c" }
      }
    }
  }
}
```

## Data Flow

### 1. Dashboard Customization (`/dashboard/customize`)

```
Merchant opens Customize page
         ↓
Fetch store.templateId
         ↓
Fetch template manifest (configSchema)
         ↓
Fetch current Store.settings
         ↓
Render dynamic forms from configSchema
         ↓
Merchant edits → PATCH /api/stores/{id} { settings }
         ↓
Saved to Store.settings JSON column
```

**Key insight:** The dashboard doesn't know about "hero" or "banner" — it reads the schema from the manifest and renders whatever fields the template declares.

### 2. Store Page (`/store/{storeId}`)

```
User visits store page
         ↓
Fetch store → get templateId + settings
         ↓
Render iframe: src=/api/templates/serve?id={templateId}&storeId={storeId}
         ↓
Serve route:
  1. Read index.html from public/templates/{id}/
  2. Read Store.settings from DB
  3. Inject config script BEFORE </head>:
     
     window.__PLATFORM_CONFIG__ = {
       storeId: "abc123",
       settings: { hero: {...}, banner: {...}, theme: {...} },
       templateId: "nike"
     };
     
  4. Inject API interceptor (appends storeId to all /api/adapters/* calls)
  5. Return modified HTML
         ↓
Template loads, reads window.__PLATFORM_CONFIG__
         ↓
Template applies settings to its components
```

### 3. API Adapter (`/api/adapters/{templateId}/{...path}`)

```
Template makes API call: GET /api/adapters/nike/products?category=men
         ↓
Adapter reads template manifest (api.mappings.products)
         ↓
Fetches from platform: GET /api/products?storeId=abc123&category=men
         ↓
Applies field mappings dynamically:
  platform: { id, name, price, images: [...], comparePrice, tags: [...] }
  mapping:  { image: "images[0]", category: "tags[0]", salePrice: "comparePrice" }
  result:   { id, name, price, image: "url", category: "Men's Shoes", salePrice: 99 }
         ↓
Returns mapped response to template
```

## Template Developer Contract

For a template to work with this platform, the developer must:

### 1. Declare configSchema in manifest.json
Tell the platform what settings merchants can configure.

### 2. Read window.__PLATFORM_CONFIG__ at app startup
```javascript
// In the React app's index.js or App.js
const config = window.__PLATFORM_CONFIG__ || {};
const storeSettings = config.settings || {};

// Apply hero settings
const heroHeadline = storeSettings.hero?.headline || "Default Headline";
const heroImage = storeSettings.hero?.image || "/default-hero.jpg";
```

### 3. Use REACT_APP_API_URL for API calls
```javascript
// .env or build config
REACT_APP_API_URL=/api/adapters/nike

// In the app
const API_URL = process.env.REACT_APP_API_URL;
fetch(`${API_URL}/products`);  // Interceptor appends ?storeId=...
```

### 4. Handle missing settings gracefully
Always provide fallbacks so the template works even if no custom config is set.

## What Template Developers Need to Do

The platform side is complete. For the **Nike template** (and future templates) to actually USE the injected config, the template developer must:

### Nike Template Changes Needed

**File: `src/App.js` or `src/index.js`**
```javascript
// Read platform config at startup
const platformConfig = window.__PLATFORM_CONFIG__ || {};
const settings = platformConfig.settings || {};

// Apply to app context or global state
window.__NIKE_CONFIG__ = {
  hero: {
    headline: settings.hero?.headline || "Get More Out of Every Run",
    subtext: settings.hero?.subtext || "Discover the latest gear",
    image: settings.hero?.image || "/default-hero.jpg",
    ctaText: settings.hero?.ctaText || "Shop Now",
  },
  banner: {
    text: settings.banner?.text || "Free shipping on orders over ৳2000",
    color: settings.banner?.color || "#111111",
    textColor: settings.banner?.textColor || "#ffffff",
  },
  theme: {
    primaryColor: settings.theme?.primaryColor || "#000000",
    accentColor: settings.theme?.accentColor || "#e74c3c",
  }
};
```

**File: `src/components/Hero.js`**
```javascript
const config = window.__NIKE_CONFIG__?.hero || {};

return (
  <div className="hero" style={{ backgroundImage: `url(${config.image})` }}>
    <h1>{config.headline}</h1>
    <p>{config.subtext}</p>
    <button>{config.ctaText}</button>
  </div>
);
```

**File: `src/components/PromoBanner.js`**
```javascript
const config = window.__NIKE_CONFIG__?.banner || {};

return (
  <div style={{ backgroundColor: config.color, color: config.textColor }}>
    {config.text}
  </div>
);
```

## Critical Insight

**The platform infrastructure is complete.** The adapter, serve route, dynamic dashboard, and database schema all work generically for any template.

**The remaining work is template-side:** Each template (Nike, SAS, restaurant, portfolio) must:
1. Declare its `configSchema` in `manifest.json`
2. Read `window.__PLATFORM_CONFIG__` at startup
3. Apply the settings to its own components

This is analogous to how Shopify themes work: Shopify provides the infrastructure, theme developers build the templates that consume the platform data.
